## 可选目录结构

```text
<deliverable-name>/
├── SKILL.md
├── examples/      # 可选：真实输入和期望输出形态
├── evals/         # 可选：可回归测试用例
├── references/    # 可选：按需加载的来源、标准、格式或质量准则
├── scripts/       # 可选：可复用、可验证、非交互式脚本
└── assets/        # 可选：模板、样式、表格或其他产物资源
```

- 只有当 agent 会反复重造同一段逻辑、需要结构化校验、需要解析文件或需要稳定生成资源时，才加入 `scripts/`。
- `scripts/` 必须非交互式，提供 `--help`，输出尽量使用 JSON、CSV、TSV 或其他结构化格式。
- 大段背景材料、引用准则和输出模板应放入 `references/` 或 `assets/`，并在 `SKILL.md` 中说明何时加载。
- 每个高频 deliverable 至少应有一个 `examples/` 示例和一个 `evals/evals.json` 回归用例。

## 工具与外部事实边界

- `SKILL.md` 本身不提供联网、数据库、代码执行或文件访问能力；这些能力由宿主 agent 决定。
- 当产物依赖当前事实、外部资料、价格、版本、政策、新闻、竞品、论文或引用时，如果宿主提供检索或浏览工具，必须先检索并列出来源、日期和不确定性。
- 如果宿主不提供相关工具，只输出基于用户输入的产物、待验证假设和检索清单，不要伪装成已完成核验。
- 用户明确要求不要联网或不要使用外部资料时，只使用用户提供材料，并标注事实边界。

## 方法

1. 重述任务和目标产物。
2. 区分事实、假设、愿望和信息缺口。
3. 选择 3 到 5 个最相关视角或方法，不默认全员上场。
4. 先形成判断，再把判断转成产物结构。
5. 输出可执行版本，并标注验证标准、停止条件和下一步。

## 输出契约

```text
产物标题:
使用场景:
关键假设:
正文:
验证标准:
风险与限制:
下一步:
```

## 失败模式

- 只输出建议清单，没有形成可交付产物。
- 用模板填空替代真实判断。
- 把未经验证的事实写成确定结论。
- 产物过大，超出当前输入和资源约束。

## 验证逻辑

- 输出必须能被用户直接拿去讨论、修改或执行。
- 必须区分事实、假设和待验证内容。
- 必须有下一步动作或验证标准。
- 如果信息不足，必须暴露信息缺口，而不是用漂亮语言补洞。

- 不要人格 cosplay。
