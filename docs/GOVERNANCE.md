# 治理模型

ArchSight Cognition 采用维护者策展制。项目欢迎外部贡献，但核心目标不是尽快扩大内容数量，而是保持认知工具的可审查性、一致性和可验证性。

本仓库不是通用 prompt 集合，也不是历史人物模拟库。每个新增工具都必须证明自己能稳定改善真实任务中的判断、表达、评审或决策，而不是只增加一种语气或一个文化符号。

## 治理边界

维护者强审以下内容：

- 命名体系：`cogp-*`、`cogm-*`、`cogt-*`、`cogv-*`、`cogd-*` 的含义和边界。
- 模板结构：frontmatter、角色、适用场景、方法、输出契约、交接、护栏、失败模式和验证逻辑。
- 安全边界：不人格 cosplay，不伪造事实，不把隐喻、修辞或学科视角当作事实证明。
- 默认安装集合：各 host 默认暴露哪些高频工具。
- 质量标准：新增内容是否能产生可执行判断，而不是泛泛评论。

可以通过提案扩展的内容：

- 新 persona、method、team、voice 和 debate。
- 新 host adapter 文档。
- 示例任务、边界测试和质量检查规则。
- 对现有工具的澄清、删减和护栏加强。

## 公开入口命名门禁

公开入口包括 `cogp-*`、`cogm-*`、`cogt-*`、`cogv-*`、`cogd-*`、CLI 命令、安装参数和 README 快速开始命令。大版本、默认安装集合变更或新增公开入口前，必须单独做命名门禁。

### 1. API / 命令名 review

发布前单独审查所有公开入口，而不只审查内容质量。每个名称都要回答：

- 用户只看名字能否猜到用途？
- 和同类入口是否一致？
- 是否暴露了内部分类、实现细节或学术黑话？

### 2. 入口分级

维护者必须区分稳定公开 API 和内部描述：

- 稳定公开入口是用户会在命令面板、README 和 adapter 中直接看到的名称。
- 内部描述可以解释实现意图，但不应成为命令名。
- 不确定的实验入口不进入默认安装集合。

### 3. 命令面板走查

发布前模拟用户只输入 `/cogm`、`/cogt`、`/cogd`、`/cogp`、`/cogv` 时看到的列表。列表里如果出现“看名字不知道干什么”的入口，先改名或移出默认安装集合，再发布。

### 4. 陌生用户 5 秒测试

对每个新入口做 5 秒测试：不看说明，只看命令名，用户是否能判断什么时候该用。不能通过时，优先改名，而不是靠长 description 补救。

### 5. Release candidate / 本地安装验证

大版本发布前先用 `npm pack --dry-run`、本地 tarball 或预发布版本做一次安装验证。验证对象至少包括：

- 打包内容是否包含新增目录和文档。
- CLI list 是否展示正确入口。
- 临时 host 目录安装后，命令面板入口是否可理解。
- 旧入口是否需要迁移、保留或清理。

### 6. 命名规范

命令名优先表达用户意图，不优先表达内部分类。当前规则：

- `auto` / `general` 只允许用于有路由职责的类别，例如 `cogt-*`、`cogm-*`、`cogd-*`。
- `cogp-*` 和 `cogv-*` 是具体 persona / voice 叶子工具，不使用 `auto` 或 `general`。
- `cogm-*` 方法名应表达用户要做的动作或判断，例如 `auto`、`priority-triage`、`critical-thinking`。
- 长名称只有在不可替代时才使用；能用短、直观、可猜的名称时，不使用内部术语。
- 目录名可以是稳定 slug，但公开命令名必须优先可理解。

## Issue 优先

新增认知工具默认先开 issue，再提交 PR。

issue 应说明：

- 想解决的大模型典型失败模式。
- 为什么现有 persona、method、team、voice 或 debate 不能覆盖。
- 该工具的最小适用场景和明确不适用场景。
- 一个边界测试：不用该工具时输出会如何空泛、误判或幻觉；使用后应如何改善。
- 涉及事实、规范、专业领域时，需要哪些外部来源或人工验证。

维护者确认方向后，再提交 `SKILL.md`、模板修改或 adapter 文档。

## 调研前处理

新增工具来自人物、流派或现代商业/技术实践时，可以先做一次“蒸馏式”调研前处理，但前处理不是最终产物。

前处理应产出：

- 一手材料和高质量二手材料清单。
- 候选心智模型，以及每个模型的证据来源。
- 三重验证结果：是否跨域复现、是否有生成力、是否有排他性。
- 明确的局限、争议、反例和不可验证部分。
- 一个最小边界测试，说明该工具能修复什么可复现失败。

前处理不得直接决定 `SKILL.md` 的口吻和身份规则。最终工具必须回到 ArchSight 模板，写成学科思维工具，而不是人物扮演、名人代言或成功学摘要。

`persona` 和 `voice` 只接收已离世人物或稳定历史传统。仍在世人物、活跃企业家、投资人、创作者和个人品牌材料如果确有方法价值，只能作为 `methods/` 的来源之一，重写为去人物中心的 `cogm-*` 方法工具。

`method` 不强制套用人物六维 research 目录。每个 `cogm-*` 默认使用轻量方法参考三件套：

```text
references/
├── sources.md
├── usage-notes.md
└── validation-cases.md
```

- `sources.md` 记录来源类别、适配依据和不迁移的内容。
- `usage-notes.md` 记录适用场景、常见误用和与其他工具的边界。
- `validation-cases.md` 记录典型输入、预期改善和失败输出特征。

如果某个 method 来自复杂学派、专业领域或高风险实践，可以额外补充 `references/research/`，但不得把人物六维模板当成 method 的默认要求。

## PR 接受标准

PR 不以“内容看起来有趣”为接受标准，而以以下问题为准：

- 这个工具是否解决了一类可复现的认知失败？
- 输出契约是否足够具体，能约束 Claude、Gemini、Codex 等模型稳定执行？
- 护栏是否覆盖主要误用方式？
- 是否给出了失败模式、验证逻辑和边界测试？
- 是否避免把历史人物、文化传统或学科隐喻包装成权威事实？
- 是否保持最小改动，没有顺手扩大项目范围？

## 拒绝标准

以下贡献通常会被拒绝或要求重写：

- 只增加口吻，不增加认知功能。
- 把 persona 写成历史人物本人、名人模仿或权威代言。
- 输出契约太抽象，无法判断成功或失败。
- 缺少失败模式、验证逻辑或边界测试。
- 需要新增运行时依赖，但没有说明必要性。
- 把高风险事实判断交给 persona 直接断言。
- 大范围重写无关文档、重排格式或混入未讨论的架构改动。

## 版本演进

项目优先采用小步、可回退的演进方式：

1. 先通过 issue 沉淀需求和边界测试。
2. 再修改模板、单个工具或 adapter。
3. 最后把稳定规则沉淀到文档和校验脚本。

如果一个方向还没有形成稳定结构，先作为示例、issue 讨论或实验性工具存在，不进入默认安装集合。

当前已蒸馏或已强化工具的状态、验收标准和后续强化流程，见 [`DISTILLATION_BASELINE.md`](./DISTILLATION_BASELINE.md)。
