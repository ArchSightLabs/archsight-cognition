# 治理模型

ArchSight Cognition 采用维护者策展制。项目欢迎外部贡献，但核心目标不是尽快扩大内容数量，而是保持认知工具的可审查性、一致性和可验证性。

本仓库不是通用 prompt 集合，也不是历史人物模拟库。每个新增工具都必须证明自己能稳定改善真实任务中的判断、表达、评审或决策，而不是只增加一种语气或一个文化符号。

## 治理边界

维护者强审以下内容：

- 命名体系：`cogp-*`、`cogt-*`、`cogv-*`、`cogd-*` 的含义和边界。
- 模板结构：frontmatter、角色、适用场景、方法、输出契约、交接、护栏、失败模式和验证逻辑。
- 安全边界：不人格 cosplay，不伪造事实，不把隐喻、修辞或学科视角当作事实证明。
- 默认安装集合：各 host 默认暴露哪些高频工具。
- 质量标准：新增内容是否能产生可执行判断，而不是泛泛评论。

可以通过提案扩展的内容：

- 新 persona、team、voice 和 debate。
- 新 host adapter 文档。
- 示例任务、边界测试和质量检查规则。
- 对现有工具的澄清、删减和护栏加强。

## Issue 优先

新增认知工具默认先开 issue，再提交 PR。

issue 应说明：

- 想解决的大模型典型失败模式。
- 为什么现有 persona、team、voice 或 debate 不能覆盖。
- 该工具的最小适用场景和明确不适用场景。
- 一个边界测试：不用该工具时输出会如何空泛、误判或幻觉；使用后应如何改善。
- 涉及事实、规范、专业领域时，需要哪些外部来源或人工验证。

维护者确认方向后，再提交 `SKILL.md`、模板修改或 adapter 文档。

## PR 接受标准

PR 不以“内容看起来有趣”为接受标准，而以以下问题为准：

- 这个工具是否解决了一类可复现的认知失败？
- 输出契约是否足够具体，能约束 Claude、Gemini、Codex 等模型稳定执行？
- 护栏是否覆盖主要误用方式？
- 是否给出了失败模式、验证逻辑和边界测试？
- 是否避免把历史人物、文化传统或学科隐喻包装成权威事实？
- 是否保持最小改动，没有顺手扩大项目范围？

## 拒绝标准

以下贡献通常会被拒绝或要求重写：

- 只增加口吻，不增加认知功能。
- 把 persona 写成历史人物本人、名人模仿或权威代言。
- 输出契约太抽象，无法判断成功或失败。
- 缺少失败模式、验证逻辑或边界测试。
- 需要新增运行时依赖，但没有说明必要性。
- 把高风险事实判断交给 persona 直接断言。
- 大范围重写无关文档、重排格式或混入未讨论的架构改动。

## 版本演进

项目优先采用小步、可回退的演进方式：

1. 先通过 issue 沉淀需求和边界测试。
2. 再修改模板、单个工具或 adapter。
3. 最后把稳定规则沉淀到文档和校验脚本。

如果一个方向还没有形成稳定结构，先作为示例、issue 讨论或实验性工具存在，不进入默认安装集合。
